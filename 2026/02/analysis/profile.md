## Top 5 data quality issues shaping this analysis

The five that changed what this analysis could say, in the order they bind:

1. **6,221 rows (10.01%) sell a product before its `LaunchDate`** - and it is 47 of the 47
   products that launch inside the window, with zero exceptions. `LaunchDate` is the one date
   rule the README does **not** state, and it is the only one the generator did not enforce.
   Product-lifecycle analysis is impossible; the rows are flagged, never dropped, because they
   are the finding.
2. **The README's four documented rules hold exactly** - row counts, the margin identity (max
   deviation **0.00**), no sales before `OpenDate`, none after `DiscontinuedDate`. That is not a
   footnote, it is the *control* that makes issue 1 a finding rather than a complaint:
   constraints were applied precisely where they were written down and nowhere else.
3. **`City` is 1:1 with `Region`** - 38 regions, 38 cities, 38 pairs. The README advertises a
   four-level geography (Country → Region → City → Pharmacy); there are three. A drill step that
   cannot change the grouping is a dead click, so `city` is a display label and the build raises
   if the two ever separate.
4. **All 32 brands sit inside exactly one category**, so a "brand performance" chart and a
   "category performance" chart are the same chart relabelled. Brand is modelled *inside*
   category and there is no top-level brand dimension for a view to treat as independent
   evidence.
5. **Zero rows dropped, zero nulls, zero orphans.** Worth stating explicitly: there is no
   cleaning story here, so every difference between this analysis and another one is a
   difference of *definition*, not of data handling.

# Conclusions - the five issues that will shape the analysis

Every number below is reproduced by `analysis/integrity.py`, which reads the **raw workbook
only**. Nothing here is computed from `data/curated/`, so a defect in `model/build.py` cannot
validate itself.

## 1. The one date rule the README does not state is the one never enforced

The README makes four factual claims and **all four hold**: every row count exact, the margin
identity at 0.00 max deviation, "no sales before `OpenDate`" at 0 violations across 11
in-window openings, "no sales after `DiscontinuedDate`" at 0 violations across 35 discontinued
products. Zero orphans on all three FKs, zero nulls, `SalesID` unique.

`LaunchDate` is the one date it says nothing about.

| | |
|---|---:|
| rows selling a product before it launched | **6,221** of 62,139 (10.01%) |
| revenue booked before the product existed | **€795,899** (9.22%) |
| products affected, of those launching in-window | **47 of 47 - zero exceptions** |
| median days traded before launch | **344** (max 719) |

**The two documented rules are the control.** Constraints were applied exactly where the README
documents them and nowhere else, which makes this an asymmetry rather than data that is loosely
built throughout. Any "new product ramp" or "time since launch" analysis is computed from a
column the fact table contradicts.

## 2. The margin rate is a constant. Only volume varies.

Four of the brief's ten questions ask where profitability differs. It doesn't.

| cut | k | margin % range | spread |
|---|---:|---|---:|
| StoreSizeBand | 3 | 28.03 - 28.06 | **0.03pp** |
| PharmacyType (Urban/Suburban/Rural) | 3 | 27.98 - 28.10 | **0.12pp** |
| Country | 8 | 27.84 - 28.16 | **0.32pp** |
| Region | 38 | 27.69 - 28.61 | **0.91pp** |
| Pharmacy | 120 | 24.73 - 29.33 | 4.61pp |
| **Category** | 5 | 21.92 - 33.58 | **11.66pp** |
| **PromoFlag** | 2 | 19.92 - 29.00 | **9.08pp** |

**Store volume is the control, and it is genuinely heterogeneous** - χ² = 6,911 on 119 df
(ratio 58.1, p≈0) against a common-rate-times-exposure model. So "everything is flat" would be
false. Stores differ enormously in *how much* they sell and not at all in *how profitably*.
Only what you sell (category) and whether you discounted it move the rate.

## 3. There is no seasonality

Both requirement lists ask for it - the page calls seasonal demand a planning problem, the DOCX
asks "are there clear seasonal patterns?"

- Monthly revenue spans €327,319 - €392,674 across 24 months (sd/mean **0.054**).
- Daily transaction count by calendar month: **KW p = 0.21**, η² = 0.021. Nothing.
- The only time structure is the **trading week**: η² = **0.384**, p = 1.2e-56. Weekday mean
  89.8 transactions vs weekend 73.0 (**-18.7%**).

That is a calendar artefact, not demand - the 2025/12 "opening hours" shape. It must be
reported as such rather than sold as a weekly demand cycle.

## 4. Promotions cost 9 margin points and buy no volume

- **Positive control - the flag is live:** realised price / list price falls 0.9848 → 0.8607
  (**-12.61%**, KW p ≈ 0). `PromoFlag` demonstrably does something.
- **The null, readable because of that control:** units per transaction 7.195 → 7.023
  (-2.39%, p = 0.031).
- **Power:** POOLED MDE at 80% / α.05 is **2.35% lift**; observed is -2.39%. Within a category
  the MDE runs **3.46% (OTC) to 7.01% (Medical Devices)**, so the five-category claim is not
  five powered tests. A real lift above the
  detection floor could not have hidden. The honest claim is **"no lift"** - not "promo hurts
  volume", since the point estimate sits at the floor.
- **Cost:** €82,709 of margin forgone against the non-promo rate, **3.42%** of total margin.

## 5. The brief's stated premise is contradicted by the file

Page requirement 4 asserts *"High-volume products with low margins reduce overall profitability
and distort performance reporting."*

Across 220 products, units vs margin % gives **Spearman ρ = +0.394 (p = 1.3e-09)** - high-volume
products carry *higher* margin. And nothing in the file loses money: **0 of 62,139** rows have
margin ≤ 0, **0 of 220** products have list ≤ cost, product margin spans 17.48% - 38.83%.

**Confound:** Brand is perfectly nested in Category - **0 of 32** brands span more than one
category. Every "brand performance" finding *is* a category finding, and the two must never be
presented as independent evidence (the 2025/06 hashtag collapse).
