## Top 5 data quality issues shaping this analysis

The five that changed what this analysis could say, in the order they bind:

1. **The grain is the customer, not the transaction.** `transaction_id` is unique across all
   1,500 rows - the check this programme runs to establish grain, and it passes - but every
   customer has exactly 75 rows and four columns never vary within one: `transaction_status`,
   `is_flagged_fraud`, `failed_reason`, `device_type`. Every rate built on those has an
   effective n of 20, and standard errors √75 = 8.66× wider than a 1,500 denominator implies.
2. **`device_type` is `customer_id mod 4`.** It is not a device. Any failure-rate-by-device
   chart is a chart of the customer id, and the build raises if the mapping ever breaks.
3. **All three dimension CSVs carry a UTF-8 BOM**, so `customer_id` parses as `﻿customer_id`
   and every join returns nulls **without raising**. The fact table has no BOM, so only the
   dimensions were affected and the fact table looked fine. `build.py` strips it and then
   asserts the key exists by name.
4. **Four `type_name` values map to two `transaction_type_id`s each**, and `ATM Withdrawal` is
   both a domestic £0.00 and an international £1.50 fee regime. Grouping by name merges two
   fee regimes and produces a failure rate belonging to neither - it reached four documents
   before `test_metrics.py` caught it. Every join in the model is on the id, and
   `dim_txn_type` carries `name_is_ambiguous` so a panel cannot group by name unknowingly.
5. **Dates are `%m/%d/%Y`, and the file does not say so.** 600 rows across 60 distinct dates
   have a day component ≤ 12 and would silently transpose under an ISO or D/M reading.
   `build.py` proves the format before parsing: day values exceed 12 and month values never
   do, so the reading is forced rather than assumed.

# Conclusions

Every number below is reproduced by `analysis/integrity.py`. Nothing is typed from memory.

## 1. The grain is the customer, not the transaction

`transaction_id` is unique across 1,500 rows, so the table *looks* like transaction grain. It is
not. Every customer has exactly **75** rows, and four columns never vary within a customer:
`transaction_status`, `is_flagged_fraud`, `failed_reason`, and `device_type`.

`amount_gbp` is barely better - 11 distinct values per customer, with a relative spread
`(max-min)/mean` of **0.3020-0.3040 for all twenty**: one seed jittered by a constant ±15% band.

**The honest unit of analysis is the customer. n = 20.**

## 2. Every rate is a fraction of a very small number

| Cut | Levels | Cell sizes (customers) |
|---|---:|---|
| `transaction_status` | 4 | 7, 5, 5, 3 |
| `device_type` | 4 | 5, 5, 5, 5 (exactly `customer_id mod 4`) |
| `customer_segment` | 4 | 6, 5, 5, 4 |
| `age_band` | 5 | 6, 5, 4, 3, 2 |
| **`region`** | **10** | **5, 3, 3, 2, 2, 1, 1, 1, 1, 1** |
| `is_flagged_fraud` | 2 | 16, 4 |
| `kyc_verified` | 2 | 16, 4 |

**Five UK regions contain exactly one customer.** A regional fraud rate is therefore 0% or 100%.

It is sharper still at transaction-type level: each of the 15 types is used by exactly **4**
customers, so every type's failure rate is a fraction with denominator 4. Every type has exactly 100
transactions and 4 customers, so the observed values are **0.750 and 0.500 and nothing else**.

## 3. The design effect

Perfect clustering with cluster size *m* gives a design effect of exactly *m*. Here m = 75, so
every standard error is **√75 = 8.66×** wider than an n = 1,500 calculation gives.

## 5. Fourteen of twenty-four dictionary claims fail

Listed in full in `brief.md`. The consequential ones: dates are M/D/YYYY not ISO; `fx_rate_used`
breaks its domestic/international rule in both directions (125 and 275 rows); 600 of 900
Declined/Reversed rows carry no `failed_reason`; there are zero negative amounts despite a
documented refund convention and 100 `Card Refund` rows; all three **dimension** CSVs carry a
UTF-8 BOM so the primary key parses as `﻿customer_id` and joins fail silently; and `type_name`
is not a key - `ATM Withdrawal` is both a domestic £0.00 and an international £1.50 fee regime.

## 6. What is real: the fee rule

`fee_charged_gbp` is the **only** column whose defect varies *within* a customer, so it is the one
finding not bounded by n = 20. **725 of 1,500 rows** deviate from `typical_fee_gbp`.

```
total charged   £750.17
total expected  £750.00
NET variance    £-0.17   (-0.023%)
GROSS under-collection  £587.11
GROSS over-collection   £587.28
```

The two errors cancel. A net fee-variance report shows -0.023% while **£1,174.39** of fees - 156%
of everything collected - sits on the wrong side of the rule. `Transfer - International` collects
£100.39 against £500.00 due; eight types whose `typical_fee_gbp` is £0.00 collect £524.40 between
them.

Total fee revenue for H1 is **£750.17** against £1.90m of transaction value: **0.04%**.
