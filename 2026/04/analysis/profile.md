## Top 5 data quality issues shaping this analysis

The five that changed what this analysis could say, in the order they bind:

1. **`movement_id` is not an identifier.** 1,001 distinct values across 15,000 rows, and it is a
   uniform draw (KS p = 0.216) - a measurement wearing an id's name. The dictionary calls it the
   primary key *and* marks it `Unique: No` in the same table. A surrogate key is generated.
2. **The fact table carries two vessel keys and they disagree on 909 rows (6.06%).**
   `vessel_key` is the real foreign key (992 of 1,000 used, 0 orphans); `vessel_id` is a
   denormalised copy - and `vessel_id` is what the dictionary documents the join on. The
   disagreement is unpatterned (duration MW p = 0.457), so it cannot be repaired by rule.
3. **`route_geometry` is constant: 1 distinct value across 15,000 rows.** All four start/end
   lon-lat columns take exactly one value each. There is no per-movement route, so the "median
   130° from its terminal" figure measures where the 50 *terminals* sit relative to one fixed
   point - a fact about the terminal list, not about any journey.
4. **`day_label` is a property of the DATE, not the movement.** A whole calendar day is "Day" or
   "Night". The brief's shift question is not merely unanswerable, it is unaskable of this
   schema, and the model refuses to name the column a shift.
5. **The archive's own data dictionary is wrong in eleven places** - including both headline
   measures. `move_duration` is documented normal and is Uniform(0,1000); `container_count` is
   documented Poisson with var/mean 164.9. A published generator spec should be a gift; this one
   has to be tested column by column before any of it can be used.

# Conclusions - the five issues that shape the analysis

Every number reproduced by `analysis/integrity.py`, which reads the **raw CSVs only**.

## 1. The archive documents its own generator - and is wrong eight times

`docs/DATA_DICTIONARY.md` publishes the *mechanism* for every column (`choice`, `faker`,
`numpy distribution=normal`). That is effectively a published null hypothesis. Eight of its
claims are false:

| Dictionary | Reality |
|---|---|
| `move_duration` ~ normal | **Uniform(0,1000)** - KS p=0.6129 vs uniform, 4.8e-48 vs normal; kurtosis -1.2065 |
| `container_count` ~ Poisson | **Uniform(0,1000)** - var/mean **164.86** |
| `regional_hub` = 3 choices | 4 - `LATAM` undocumented |
| `vessel_category` = 3 choices | 4 - `Container` undocumented |
| `build_year` 1990-2023 | 1900-2023 |
| `movement_id` = Primary Key | 1,001 distinct over 15,000 rows (and marked `Unique: No` in the same table) |
| fact has 6 columns | also `date_id`, `vessel_key`, `vessel_category` |
| `dim_time` ≈ 5,000 rows | 1,461 |

## 2. There is no unique row key, and one join key is corrupt

`movement_id` is a **uniform draw over 0-1000** (KS p=0.2160), 5-26 rows sharing each value.
Zero exact duplicate rows, so the rows are distinct - but nothing identifies them.

The fact carries **two vessel keys**. `vessel_key` is the real FK (992 of 1,000 used, 0
orphans). `vessel_id` is a denormalised copy that **disagrees with the dimension on 909 of
15,000 rows (6.06%)**, and the mismatch is unpatterned (container_count MW p=0.164,
move_duration p=0.457). The denormalised `vessel_category`, by contrast, agrees on all 15,000.

## 3. Nothing predicts `move_duration`

| axis | k | KW p | η² |
|---|---:|---:|---:|
| regional_hub | 4 | 0.7115 | 0.00009 |
| vessel_category | 4 | 0.0683 | 0.00048 |
| shift | 2 | 0.0601 | 0.00024 |
| terminal_id | 50 | 0.7154 | 0.00287 |
| fiscal_year | 4 | 0.7123 | 0.00009 |
| build_year (Spearman) | - | 0.4771 | ρ=+0.0058 |
| container_count (Spearman) | - | 0.9146 | ρ=-0.0009 |

The largest effect in the file is *vessel build year* as a 123-group cut, at η²=0.0079; the largest
of the axes the brief actually names is *terminal*, at η²=0.0029. And terminals take equal work by
construction: χ²=41.0 on 49 df (ratio **0.84**, p=0.78), range 262-329 movements.

## 4. The Suez disruption is not in the data

The brief's headline ask. Suez week (23-29 Mar 2021) vs every other day: move_duration
**MW p=0.504**, movements/day p=0.056, containers/day p=0.135. Within 2021, March and April
average **260.5 movements/month against 247.9 for the other ten - 5.1% ABOVE**, and the
twelve months do not differ (χ² p=0.1200).

## 5. THE POSITIVE CONTROL - one thing here is real, and it is the dangerous one

Movement **count** grows monotonically:

```
2021 = 3,000   2022 = 3,750 (+25.0%)   2023 = 4,050 (+8.0%)   2024 = 4,200 (+3.7%)
48 monthly counts vs time: Spearman rho = +0.827, p = 4.35e-13
daily chi2/df = 1.1731 vs simulated multinomial mean 0.9980, 95th pct 1.0581, MAX 1.1418
```

It exceeds even the **maximum** of 1,000 simulated multinomials, so it is not allocation noise.
And it is **only in the count** - `move_duration` by year KW p=0.7123, `container_count` by
year p=0.1748.

**Why this is the dangerous signal.** 2021 is the lowest year, so the ramp reads as *"Suez
depressed 2021 and we recovered"*. There is no March 2021 dip, and the ramp continues for three
more years with no event to explain it.

## Also carried into G3

- **`shift` is a property of the DATE.** `dim_time` has one row per day, so an entire calendar
  day is "Day" or "Night". A terminal running two shifts cannot be represented - the brief's
  shift question is not merely unanswerable, it is unaskable of this schema.
- **`regional_hub` has no geography.** Longitude by hub KW p=0.1899; coordinates uniform over
  the globe (lon KS p=0.5227, lat p=0.4126); 7 terminals below 60°S, 4 above 70°N. Terminal
  names are faker *person* names.
- **Two geo columns, two serialisations.** `dim_terminal.port_location` is valid JSON;
  `fact.route_geometry` is a Python `repr` with single quotes and `json.loads` fails on it -
  and it is **constant**: one distinct value across all 15,000 rows (see the column table
  above, which flagged this at G2). There is no per-movement route. The single fixed endpoint
  sits a median **130° (~14,433 km)** from the terminal a row is filed against, which measures
  the spread of the 50 terminals, not the geometry of any journey.
- **`terminal_capacity` does not exist**, as the archive brief itself concedes.
